# 本机 100 HOST 指标容量基线

本记录用于校准数据库行宽和曲线查询成本，不作为规划目标容量的通过证明。工作负载按 100 个 HOST、每个 HOST 50 条指标序列、30 秒采样间隔生成一天数据：共 288,000 个 Agent 批次、14,400,000 个指标样本和 5,000 条资源指标序列。

测试使用全新 Flyway V25 PostgreSQL 17.11 数据库，容器限制为 4 vCPU / 6 GiB；隔离 JVM 应用使用 `-Xmx1g`。项目、HOST、Agent、批次和样本均为本次临时数据。`scripts/benchmark-100-hosts.sql` 只允许连接到名为 `geek_monitor_benchmark` 的数据库，并在检测到已有容量基准 Agent 时拒绝重复灌数。

样本通过批量 SQL 直接写入，不是 100 个真实 Agent 经 HTTP 连续上传。Agent 批次写入 288,000 行耗时 4.544 秒；指标写入 14,400,000 行耗时 411.728 秒，约 35,000 行/秒。单个 `metric_sample` 表及其索引共 5,819,580,416 字节，其中 heap 为 2,534,096,896 字节、索引为 3,284,746,240 字节，约 404 字节/样本。按三天原始数据线性外推约 17.5 GB；该估算不含 WAL、备份、额外空间余量及其他业务表。

样本写入后，通过隔离 JVM 的认证指标 API 查询单个 HOST 的 24 小时曲线，50 条序列返回 71,450 个聚合点，响应 7,338,642 字节。首次请求耗时 1.092 秒，随后四次为 0.771、0.608、0.568、0.624 秒。7、30、180 天窗口的一小时聚合请求均返回 HTTP 200，耗时分别为 0.099、0.090、0.086 秒、响应约 143 KB；数据库只含一天原始数据且没有历史 rollup，因此这些请求不验证长期 rollup 数据内容。

同一版本另通过真实 Agent HTTP 链路执行突发写入：脚本先经首次安装、资源创建、一次性 enrollment 和 Agent 注册 API 建立 100 个独立 Agent，再以 16 个并发工作线程对 `/api/v1/agents/{id}/batches` 提交每节点 100 批、每批 50 条指标。10,000 个请求全部返回 HTTP 202，均为可信且非重复；共落库 500,000 条样本、5,000 条序列。两次运行分别耗时 29.512/30.259 秒，吞吐 338.85/330.48 批/秒，样本吞吐 16,942/16,524 条/秒；请求 P50/P95/P99 分别为 34.35/122.62/183.52 毫秒和 36.29/124.25/183.54 毫秒，最大值为 321.86/421.91 毫秒。第二次运行后 `metric_sample` 表及索引共 200,032,256 字节，整个数据库共 213,898,931 字节；同次认证曲线 API 查询返回 50 条序列、2,550 个点，耗时 126.45 毫秒。样本时间覆盖每节点 50 分钟，但被压缩至约半分钟提交；这是一轮短时并发突发测试，不是全天持续采集。

本次验证了 SQL 批量写入、真实 Agent HTTP 批次写入和单 HOST 曲线读取。容器为 6 GiB 而非规划的 8 GiB；SQL 灌数绕过 Agent HTTP 入口和逐批事务；HTTP 测试虽使用 100 个独立凭据和真实逐批事务，但只在约 30 秒内突发回放每台 50 分钟的样本，并非 100 个真实 Agent 进程按 30 秒周期持续运行。通知风暴、磁盘不足故障和七天运行也未覆盖。因此 100 HOST 目标规模、目标硬件和 P4 验收仍未通过。

真实 HTTP 压测可在只绑定回环地址的空白实例上运行 `python3 scripts/benchmark-agent-http.py --base-url http://127.0.0.1:18084 --hosts 100 --batches-per-host 100 --concurrency 16`；脚本拒绝非回环 URL 和已初始化实例，会使用 `admin@biliwind.com` 完成测试初始化，并在批次写入后认证查询曲线 API。SQL 大样本存储校准使用 `psql -f scripts/benchmark-100-hosts.sql`。两个脚本都只应连接一次性 `geek_monitor_benchmark` 数据库，不要接入开发库、生产库或持久化卷。
