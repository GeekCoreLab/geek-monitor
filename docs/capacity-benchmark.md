# 本机 100 HOST 指标容量基线

本记录用于校准数据库行宽和曲线查询成本，不作为规划目标容量的通过证明。工作负载按 100 个 HOST、每个 HOST 50 条指标序列、30 秒采样间隔生成一天数据：共 288,000 个 Agent 批次、14,400,000 个指标样本和 5,000 条资源指标序列。

测试使用全新 Flyway V25 PostgreSQL 17.11 数据库，容器限制为 4 vCPU / 6 GiB；隔离 JVM 应用使用 `-Xmx1g`。项目、HOST、Agent、批次和样本均为本次临时数据。`scripts/benchmark-100-hosts.sql` 只允许连接到名为 `geek_monitor_benchmark` 的数据库，并在检测到已有容量基准 Agent 时拒绝重复灌数。

样本通过批量 SQL 直接写入，不是 100 个真实 Agent 经 HTTP 连续上传。Agent 批次写入 288,000 行耗时 4.544 秒；指标写入 14,400,000 行耗时 411.728 秒，约 35,000 行/秒。单个 `metric_sample` 表及其索引共 5,819,580,416 字节，其中 heap 为 2,534,096,896 字节、索引为 3,284,746,240 字节，约 404 字节/样本。按三天原始数据线性外推约 17.5 GB；该估算不含 WAL、备份、额外空间余量及其他业务表。

样本写入后，通过隔离 JVM 的认证指标 API 查询单个 HOST 的 24 小时曲线，50 条序列返回 71,450 个聚合点，响应 7,338,642 字节。首次请求耗时 1.092 秒，随后四次为 0.771、0.608、0.568、0.624 秒。7、30、180 天窗口的一小时聚合请求均返回 HTTP 200，耗时分别为 0.099、0.090、0.086 秒、响应约 143 KB；数据库只含一天原始数据且没有历史 rollup，因此这些请求不验证长期 rollup 数据内容。

同一版本先通过真实 Agent HTTP 链路进行两次 500,000 样本短测：每次由 100 个独立 Agent 凭据各提交 100 批、每批 50 条指标，10,000 个请求均返回 HTTP 202、无失败，耗时 29.512/30.259 秒，吞吐 338.85/330.48 批/秒，P95 为 122.62/124.25 毫秒。

随后每节点提交 2,880 批，完整回放 100 台主机一天的 14,400,000 个样本。288,000 个 HTTP 请求全部返回 HTTP 202，响应均标记可信且非重复；数据库核对为 100 个 Agent、288,000 个批次、14,400,000 条可信样本和 5,000 条序列。写入耗时 2,387.815 秒，吞吐 120.61 批/秒、6,030.62 样本/秒；请求延迟 P50/P95/P99 为 74.68/377.45/399.13 毫秒，最大 3,000.71 毫秒。写后认证曲线 API 返回 HTTP 200、50 条序列、72,050 个点，耗时 962.21 毫秒。最终 `metric_sample` 表及索引为 5,819,604,992 字节，整个数据库为 5,948,987,059 字节，Flyway 为 V25。

此前 4 vCPU / 6 GiB SQL 和 HTTP 记录是历史基线；更新的 4 vCPU / 8 GiB 容器日量验收及 500 项真实调度结果见下节。样本时间仍被压缩，HTTP 写入客户端模拟 100 组独立 Agent 凭据，没有运行 100 个 Agent 进程。新结果补齐了规划的合计容器 CPU/内存配额，但不证明指定物理硬件、真实 24 小时采集节奏、长期稳定性或 7 天试运行；磁盘不足故障也未覆盖，P4 仍未通过。本机 Outbox 5,000 事件突发和渠道限速演练见产品规划第 12 节。

真实 HTTP 日量压测可在只绑定回环地址的空白实例上运行 `python3 scripts/benchmark-agent-http.py --base-url http://127.0.0.1:18084 --hosts 100 --batches-per-host 2880 --concurrency 16`；脚本拒绝非回环 URL 和已初始化实例，会使用 `admin@biliwind.com` 完成测试初始化，并在批次写入后认证查询曲线 API。SQL 大样本存储校准使用 `psql -f scripts/benchmark-100-hosts.sql`。这些脚本都只应连接一次性 `geek_monitor_benchmark` 数据库，不要接入开发库、生产库或持久化卷。

## 4 vCPU / 8 GiB API 日量和调度容量复验

2026-10-12 在全新隔离 PostgreSQL 17.11 与 JVM 应用上按规划总配额复验：应用容器限制为 1 vCPU / 2 GiB，数据库容器限制为 3 vCPU / 6 GiB，合计 4 vCPU / 8 GiB。100 组独立 Agent API 凭据各提交 2,880 个批次，每批 50 条可信指标；共 288,000 个 HTTP 请求、14,400,000 条可信且非重复样本，零失败。压缩回放耗时 3,624.676 秒（约 60 分 25 秒），79.46 请求/秒、3,972.77 样本/秒；请求延迟 P50/P95/P99/最大值为 111.48/597.62/718.36/6,609.57 毫秒。认证曲线 API 返回 HTTP 200、50 条序列和 72,000 个点，耗时 1,390.54 毫秒。数据库最终大小为 6,162,847,411 字节。末次内存采样为应用 513.8 MB、数据库 333.1 MB；这是结束时快照，不是运行峰值。

同一容器配额下还运行 `scripts/e2e-scheduler-capacity.py`，创建 100 个 HOST 和 500 个 HTTP 检查，经真实调度器访问隔离 Nginx 探针。500/500 均完成且状态为 UP，总耗时 6.83 秒；系统状态 API 记录的调度至结果延迟 P95 为 3,494 毫秒，结束时 due/running/stale 均为 0。第一次尝试发现 JVM 继承宿主 HTTP 代理后会把探测请求送往代理，未直连 DNS 校验得到的地址；修复 `HttpCheckService` 后以继承代理环境重新运行通过。检查和 Webhook OkHttp 客户端现在明确禁用代理，保证请求落到经校验的目标地址。

这些结果使用一次性容器和本机合成客户端；日量时间压缩至约一小时，Agent 客户端生成器在容器配额之外，资源数字是最终快照而非峰值，也没有复刻目标物理机器。它证明该隔离容器配额下的完整 API 日量和 500 项调度用例通过，不证明真实 24 小时采集、物理目标硬件、磁盘耗尽或连续 7 天运行。复跑 500 项调度测试需要空白一次性应用、仅用于该测试的数据库，以及从应用容器可达的 `http://scheduler-probe/` HTTP 探针；脚本只接受回环应用 URL，并拒绝已初始化实例。

## PostgreSQL 数据目录耗尽与恢复演练

2026-10-12 在 PostgreSQL 17.11/JVM 隔离栈上把一次性数据库数据目录放入 512 MiB tmpfs，并将数据库容器限制为 2 GiB。脚本先确认数据库容器是指定 PostgreSQL 17 镜像、`PGDATA` 指向该 tmpfs，应用是回环地址上的空白实例，然后将 tmpfs 填至 100%。此时就绪 API 仍返回 `UP`，初始化写操作返回 HTTP 500；响应只包含通用错误 ID 和空 stack 字段，不泄露 `No space left on device` 或数据库异常细节。`install/status` 仍为未初始化，证明失败事务没有留下管理员/项目的部分状态。删除测试填充文件后，数据库可用空间恢复到 474,220 KiB，初始化返回 HTTP 201、管理员登录返回 HTTP 200，就绪状态恢复/保持 `UP`。

复跑时预先启动名为 `geek-monitor-disk-pressure-db` 的 PostgreSQL 17 Alpine 容器，使用 `--memory 2g --tmpfs /var/lib/postgresql/data:rw,size=512m`，并在仅测试用途的网络中启动名为 `geek-monitor-disk-pressure-app` 的空白 JVM 应用，绑定 `127.0.0.1:18091`；随后运行 `python3 scripts/e2e-database-space-pressure.py --base-url http://127.0.0.1:18091`。脚本会确认两个容器运行在同一临时网络、应用准确连接 `db` 别名下的 `geek_monitor` 测试库、该库仍未初始化，且应用只绑定回环地址；同时拒绝非回环 URL、非 PostgreSQL 17/非默认 `PGDATA`、未限定 tmpfs 或大于 2 GiB 的数据目录。无论测试结果如何，都会在 `finally` 中移除填充文件。演练使用临时 tmpfs，不触碰开发库、七天观察库或持久卷。它验证磁盘耗尽时事务回滚和空间恢复后的可用性，不代表目标硬件持续写入或生产磁盘故障矩阵。

## PostgreSQL 监控目标停机与恢复

2026-10-12 在当前源码构建的 V27 JVM 镜像上，以内部 Podman 网络和两个一次性 PostgreSQL 17.11 实例运行 `scripts/e2e-database-outage.py`。独立服务库始终在线；调度器先将目标 PostgreSQL 判为 `UP`，停止目标容器后将数据库监控转为 `DOWN`，记录通用 `TIMEOUT` 分类并打开 `AVAILABILITY` 事件。以固定测试 IP 重启目标库后，监控恢复 `UP`，同一事件变为 `RESOLVED`，应用就绪保持 `UP`。该 E2E 覆盖真实定时调度和状态机，不模拟 SQL 异常或生产网络延迟。

复跑命令为 `./gradlew build --no-daemon --console=plain`、`podman build --tag localhost/geek-monitor:db-outage-e2e --file src/main/docker/Dockerfile.jvm .`，然后执行 `python3 scripts/e2e-database-outage.py --app-image localhost/geek-monitor:db-outage-e2e --timeout 120`。脚本拒绝占用的回环端口，随机创建 `--internal` 网络、一次性 tmpfs 数据库和回环绑定的应用容器，确认 Flyway 为 V27、目标数据库 IP 在应用的精确允许 CIDR 内，退出时移除所有临时容器和网络；它不连接开发库、七天观察库或持久卷。
